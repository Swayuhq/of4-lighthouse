OF4 Lighthouse · connectors · living build record

Two ways to plug a channel into Lighthouse, and the one we use now

Lighthouse needs to read every comment a business gets and post a reply back. We tried the same Facebook Page both ways: through Composio, a ready made connector service, and straight through Meta with our own app. Both worked. This page records what we measured, what we chose for the prototype, and how the build moves forward.

Decision

Composio now, our own connector later

Prototype, from 30 October Composio

Facebook goes live in Lighthouse through Composio. It replied on a real Page without waiting for Meta's app review, so the team can see real comments this week.

Product, after the prototype Our own Meta connector

Built from scratch on Meta's own interface once our Meta app passes review. Faster per call and no middle company holding the owner's login.

What makes the switch cheap One file changes

Every channel enters Lighthouse through one socket, src/connectors.ts. Swapping Composio for our own connector replaces one adapter. The inbox, counts and replies stay as they are.

How it fits Lighthouse

One socket, any connector behind it

Every channel turns its own item into one strict message shape. Everything after the socket sees only that shape, so the owner's inbox does not know or care which path brought a comment in.

Adapterread pulls items, send posts a reply. Composio today, Meta direct later
One message shapeZod strict check. Anything else is refused and counted
Postgres storeeach message written once, every change an event
Agentsreader, insights, reply draft the owner can edit
Inboxarrived = answered + waiting + spam, missed is 0
// src/connectors.ts: the adapter grows a send beside read
type Adapter = {
  label: string;
  mode: 'sample' | 'live';     // facebook moves from sample to live
  read: (raw) => Message | null;
  send?: (platformId, text) => Promise<string>;   // new: the reply id from the platform
};

WhatsApp, Instagram and Google reviews stay on saved sample files until each one has a live adapter.

30 Oct

Cost of checking measured Done

Counted from the code: one Facebook check makes 27 calls, not 5. A 30 second check uses about 14,400 calls a day per open inbox. Composio Hobby allows 100,000 a month; Pro is 29 dollars plus 0.0003 dollars a call, about 700 dollars per owner a month at this rate. Meta allows 4,800 calls times engaged users a day per Page. Polling does not survive scale; webhooks do.

30 Oct

WhatsApp through Meta's webhook Done

Meta pushes each message to Lighthouse. Three locks: the verify handshake (wrong token 403), a signature check with the app secret (unsigned 401), and a tunnel guard so only the webhook answers through the public tunnel (inbox 404). 103 of 103 tests; the guard's test goes red when the guard is removed. A message from a real phone was not tested. Code: src/whatsapp.ts, app/api/webhooks/whatsapp/route.ts, proxy.ts.

Found while building

Things that cost time, so the next person skips them

Composio wants the comment's own number

Meta names a comment postId_commentId. Composio's reply action reads the part before the underscore as a Page and fails. Send only the part after the last underscore.

Page ids come from Composio's own list

The first Composio reply failed with "Page not found in your managed pages". Take the Page id from FACEBOOK_LIST_MANAGED_PAGES, never from a Meta id.

The personal key fits one endpoint only

The Composio key used here works on its MCP endpoint and returns 401 on the developer REST interface. The setup for many owners needs a different key.

Meta offers only the use cases you add

Our Meta app showed only WhatsApp permissions until the Pages use case was added. Page read and reply need pages_read_engagement, pages_read_user_content and pages_manage_engagement.
